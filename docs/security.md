# Безпека

## Модель загроз

API доступний з інтернету, адмінка — лише з VPN. Нападник може: підбирати токени, засипати сервер запитами,
відкривати тисячі потоків, підставляти заголовки з чужою адресою, красти токени з журналів чи
з пристрою. Власний пристрій може зламатись і почати шаленіти. Джерело (alertd) може бути
недоступним.

Мета: без чинного токена — нічого; з токеном — лише те, що йому дозволено, і не більше, ніж
дозволено; викрадений токен можна миттєво відкликати; жоден клієнт не може погіршити роботу
іншим; навіть повністю зламана служба не має куди з'єднатися й нічого не може змінити на сервері.

## Захист

| Рівень | Захист |
|---|---|
| Мережа | alertcast слухає лише loopback; публічно — тільки через reverse proxy з TLS; локальний API (`/health`, `/stats`) — примусово loopback |
| Вихідні з'єднання | systemd `IPAddressDeny=any`, `IPAddressAllow=localhost`: служба може з'єднатися лише з цим сервером (alertd). Навіть виконавши чужий код, вона нікуди не передасть даних |
| Токени | 256 біт випадковості, префікс `ac_`; у БД лише SHA-256; показуються один раз; дешева перевірка формату до хешування |
| Відмови | одна й та сама `401` на все: немає токена, невідомий, прострочений, чужа адреса, токен у адресі без дозволу. Невідомі шляхи API теж вимагають токен — структуру API не перебрати |
| Підбір | ліміт запитів з адреси до перевірки токена; після 10 невдалих спроб за 10 хв адреса блокується на 15 хв (IPv6 — уся /64). Пам'ять під облік адрес обмежена |
| Обмеження токена | запитів на хвилину, одночасних потоків, термін дії, дозволені регіони (з вкладеними), дозволені адреси/мережі, дозвіл на токен у адресі |
| Потоки | ліміти на токен, на адресу й загалом; повільний клієнт не має черги — він отримує лише останній стан; запис має дедлайн 15 с, завислий клієнт відключається |
| Адреса клієнта | заголовкам віримо лише від локального proxy; `CF-Connecting-IP` — лише якщо до proxy з'єднався вузол Cloudflare; для VPN-входу — окреме правило |
| Токен у адресі | лише для токенів із дозволом; на VPN-вході не приймається взагалі |
| Браузер | сесія `__Host-ac_session` (`HttpOnly`, `Secure`, `SameSite=Strict`, 12 год) замість токена в адресі; вхід лише токеном у заголовку й лише з того самого `Origin`; сесія підкоряється всім обмеженням токена й гасне разом із ним |
| Живучість | `Type=notify` + `WatchdogSec=30`: служба кожні 10 с підтверджує systemd, що справді відповідає (стан не заблоковано, HTTP працює); зависла служба перезапускається, а не лише впала |
| Керування з консолі | Unix-сокет `/run/alertcast/admin.sock` (0600, тека 0750); ядро повідомляє uid клієнта (SO_PEERCRED) — приймаються тільки root і сама служба. Пароль і 2FA адміна змінюються лише так |
| Адмінка | слухає лише loopback (інше не запуститься); назовні — лише через VPN-сайт proxy. Вхід: пароль (PBKDF2-SHA256, 600 000 ітерацій) + TOTP; кожен код 2FA приймається один раз, і після перезапуску теж. Після невдачі — пауза 1–16 с, 5 невдач з адреси — блок на 15 хв, 20 загалом — вхід закрито для всіх на 5 хв; спроби з однієї адреси не йдуть паралельно |
| Сесія адміна | cookie `__Host-ac_admin` (`HttpOnly`, `Secure`, `SameSite=Strict`); 30 хв простою (фонові оновлення сторінки його не продовжують), максимум 12 год, до 5 сесій. Зміни — лише з заголовком `X-CSRF`, `Origin` цього ж сайту й `Content-Type: application/json`; невідомі поля JSON відхиляються |
| Сторінки адмінки | статичні файли, CSP `script-src 'self'` без inline-скриптів і стилів, `frame-ancestors 'none'`, HSTS; дані вставляються лише як текст; до входу не видно ні версії, ні налаштувань |
| Відкликання | миттєве: відкриті потоки токена закриваються одразу |
| Запити | лише `GET`/`HEAD`; заголовки ≤ 16 КБ; тайм-аути заголовків і читання; до 64 регіонів у запиті; ID — лише цифри |
| Відповіді | JSON з `nosniff`, `no-store`, CSP `default-src 'none'`; без CORS (інші сайти не прочитають відповіді через браузер користувача); публічні сторінки (`/`, `/docs`) — з жорстким CSP; тестова область на них не потрапляє |
| Джерело | alertd — лише loopback (http дозволено тільки для loopback); без перенаправлень; обмеження розміру відповіді й рядка потоку; сторожовий таймер; перевірка версії API і `epoch` бази alertd |
| Процес | користувач `alertcast`, без привілеїв і capabilities, `ProtectSystem=strict`, приватні `/tmp` і пристрої, фільтр системних викликів (`@system-service`, без `@privileged` і `@resources`), `MemoryDenyWriteExecute`, пам'ять ≤ 320 МБ; `systemd-analyze security` — **0.9 SAFE** |
| Файли | `alertcast.env` — `600 root`, тека `/etc/alertcast` — `700`; БД — `/var/lib/alertcast` (`750 alertcast`), файли `600`. У БД — хеші токенів, хеш пароля й секрет 2FA адміна: резервні копії БД зберігайте так само закрито |
| Ланцюжок постачання | одна пряма залежність (go-sqlite3, чистий Go без cgo і JIT); `govulncheck` у CI; дії GitHub закріплені за комітами; релізи з атестацією походження |

## Перевірено тестами

- 401 однакова для 8 різних причин відмови; заголовки й формати передачі токена;
- ліміт запитів, блокування підбору (IPv4 і IPv6 /64), обмеження пам'яті під облік адрес;
- справжня адреса: 12 сценаріїв, зокрема підставлений `CF-Connecting-IP` з VPN;
- обмеження регіонів (предок, сусід, інша область; v3 не «протікає»);
- ліміти потоків на токен, адресу й загалом; відкликання, зміна й завершення терміну посеред потоку;
- адмін-сокет: права, перевірка всіх полів, сирий токен ніколи не потрапляє в БД;
- фазинг запитів API і потоку від alertd;
- наскрізні тести бінарника під тим самим фільтром системних викликів, що в systemd, і під
  забороною виконуваної пам'яті;
- сесії: атрибути cookie, вхід лише заголовком, чужий `Origin`, обмеження токена, відкликання, прострочення, ліміти;
- сторожовий таймер: сигнал є лише від живої служби, зникає, коли вона «зависла»;
- адмінка: вектори RFC 6238, повтор коду (і після перезапуску), паузи й блокування входу,
  паралельні спроби, простій і абсолютний термін сесії, CSRF, чужий `Origin`, не-JSON, невідомі
  поля, розмір тіла, сторінки без входу, `admin setup` лише з сокета;
- мутаційне тестування: понад 35 навмисних поломок захисту й логіки — кожну ловить тест.
